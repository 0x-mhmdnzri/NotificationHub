# داستان ساخت NotificationHub  
### از یک API ساده تا یک پلتفرم واقعی اعلان‌رسانی

> این نوشته برای کسانی است که می‌خواهند **بدون اصطلاحات سنگین** بفهمند در این پروژه چه کرده‌ایم، **چرا** آن کار را کرده‌ایم، و پشت صحنه چه مفاهیم نرم‌افزاری واقعاً پیاده شده‌اند — نه فقط روی اسلاید.

---

## یک جمله معرفی

**NotificationHub** سرویسی است که به برنامه‌ات می‌گویی:  
«این پیام را برای این کاربر، از این کانال بفرست»  

و خودش بقیه را انجام می‌دهد: صف، قالب، رضایت کاربر، تلاش مجدد، وضعیت ارسال، کمپین گروهی، و اتصال به ایمیل / پیامک / پوش / چت.

---

## مشکل واقعی چه بود؟

در بیشتر محصولات، ارسال اعلان این‌طور شروع می‌شود:

1. یک `HttpClient` مستقیم به SendGrid  
2. بعد SMS با Twilio  
3. بعد پوش با FCM  
4. بعد متوجه می‌شوی اگر سرور قطع شود، پیام گم می‌شود  
5. بعد می‌خواهی OTP را زودتر از خبرنامه بفرستی  
6. بعد حقوقی می‌گوید رضایت بازاریابی را چک کن  

نتیجه: کد پراکنده، بدون قرارداد مشترک، سخت برای تست و سخت برای رشد.

هدف این پروژه این بود که **یک هسته پایدار** داشته باشیم و هر کانال مثل **افزونه** اضافه شود — نه اینکه هسته با هر provider جدید متورم شود.

---

## نقشه راه کارهایی که انجام شد (به زبان ساده)

### ۱) هسته قابل گسترش (معماری Microkernel / Plugin)

**چه کار کردیم؟**  
هسته فقط مسئولیت‌های مشترک را دارد: پذیرش درخواست، صف، وضعیت، قالب، رضایت، و بارگذاری افزونه‌ها.  
هر کانال (ایمیل، SMS، پوش، …) یک **پلاگین** جداست.

**چرا؟**  
اگر فردا بخواهی به جای SendGrid از SES استفاده کنی، نباید کل سیستم را دست بزنی. پلاگین عوض می‌شود؛ هسته ثابت می‌ماند.

**مفهوم نرم‌افزاری:**  
- معماری Microkernel  
- اصل Open/Closed (باز برای توسعه، بسته برای تغییر هسته)  
- جداسازی قرارداد (Abstractions) از پیاده‌سازی (Plugins)

---

### ۲) ساختار پوشه‌ها و Solution درست

**چه کار کردیم؟**  
پروژه را از یک ساختار درهم به لایه‌های مشخص بردیم:

| لایه | نقش ساده |
|------|----------|
| **Host** | درِ ورودی — API و اتصال همه چیز |
| **Kernel / Abstractions** | قراردادهایی که پلاگین‌ها باید رعایت کنند |
| **Domain** | قوانین کسب‌وکار خالص |
| **Application** | سناریوهای کاربر (فرمان‌ها و کوئری‌ها) |
| **Infrastructure** | دیتابیس، صف، Hangfire، … |
| **Plugins** | کانال‌های واقعی ارسال |

**چرا؟**  
وقتی همه چیز در یک پروژه باشد، بعد از چند ماه نمی‌فهمی مرزها کجاست. ساختار درست یعنی تیم بعدی هم سریع راه می‌افتد.

**مفهوم نرم‌افزاری:**  
- Clean Architecture / لایه‌بندی  
- Composition Root (همه ثبت‌ها در Host)

---

### ۳) مدل دامنه غنی (DDD واقعی، نه فقط اسم)

**چه کار کردیم؟**  
به‌جای اینکه اشیاء فقط «جعبه فیلد» باشند (Anemic Model)، موجودیت‌هایی مثل **Notification** و **Campaign** رفتار دارند:

- چه زمانی می‌توان Accepted شد؟  
- چه زمانی Suppress می‌شود؟  
- کمپین از چه وضعیتی به چه وضعیتی می‌رود؟  

قوانین داخل دامنه نشستند، نه داخل Controller.

**چرا؟**  
اگر قانون «پیام قبلاً لغو شده را دوباره نفرست» فقط در یک endpoint باشد، فردا از مسیر دیگری دور زده می‌شود. قانون باید در خود مدل باشد.

**مفهوم نرم‌افزاری:**  
- Domain-Driven Design  
- Aggregate و Invariant  
- Domain Event  
- Ubiquitous Language (زبان مشترک کسب‌وکار و کد)

---

### ۴) نتیجه عملیات به‌صورت صریح (Result Pattern)

**چه کار کردیم؟**  
به‌جای اینکه هر خطای کسب‌وکار را با Exception پرتاب کنیم، خروجی‌ها را این‌طور مدل کردیم:

- **موفق** → داده  
- **شکست قابل انتظار** → کد خطای پایدار (مثلاً `notification.not_found`)

Exception برای چیزهای غیرمنتظره ماند (دیتابیس قطع، باگ برنامه‌نویس).

**چرا؟**  
«کاربر پیدا نشد» یک شاخه عادی کسب‌وکار است، نه فاجعه سیستم. با Result، API می‌تواند ۴۰۴/۴۰۹ درست برگرداند و مانیتورینگ هم اشتباهی آلارم قرمز نمی‌زند.

**مفهوم نرم‌افزاری:**  
- Result Pattern / Railway-oriented thinking  
- تفکیک *expected failure* از *unexpected failure*  
- ProblemDetails در مرز HTTP

---

### ۵) CQRS سبک با MediatR

**چه کار کردیم؟**  
هر عمل مهم یک **Command** یا **Query** شد (مثلاً AcceptNotification، GetCampaign).  
Handlerها منطق را اجرا می‌کنند؛ Validation در Pipeline می‌آید.

**چرا؟**  
کنترلر لاغر می‌ماند. تست هر سناریو ساده‌تر است. می‌توانی قبل از Handler، اعتبارسنجی و مجوز را یک‌جا اعمال کنی.

**مفهوم نرم‌افزاری:**  
- CQRS (حداقل در لایه Application)  
- Mediator  
- Pipeline Behaviors (Cross-cutting)

---

### ۶) قابلیت اطمینان پیام‌رسانی: Outbox + Inbox + Hangfire

**چه کار کردیم؟**  
وقتی اعلان پذیرفته می‌شود:

1. وضعیت در دیتابیس ذخیره می‌شود  
2. همان تراکنش، یک ردیف **Outbox** می‌نویسد  
3. بعد از Commit، **Hangfire** (یا worker) آن را به RabbitMQ می‌فرستد  

اگر مصرف‌کننده پیام را دو بار ببیند، **Inbox** جلوی پردازش تکراری را می‌گیرد.

**چرا؟**  
«ذخیره در DB موفق شد ولی صف از دست رفت» یکی از کلاسیک‌ترین باگ‌های سیستم‌های توزیع‌شده است. Outbox این شکاف را می‌بندد.

**مفهوم نرم‌افزاری:**  
- Transactional Outbox  
- Inbox / Idempotency  
- At-least-once delivery + پردازش امن  
- Job durability با Hangfire (نه به‌عنوان message broker، بلکه برای اجرای مطمئن کار)

---

### ۷) صف و Workerهای RabbitMQ به‌سبک تولید

**چه کار کردیم؟**  

- Prefetch برای کنترل فشار از سمت broker  
- Semaphore برای محدودیت همزمانی داخل اپلیکیشن  
- صف‌های جدا per-channel (`notifications.email`, …)  
- صف **critical** تا OTP زیر خبرنامه نماند  
- DLQ و retry با تأخیر  
- ACK فقط بعد از پردازش موفق  

**چرا؟**  
اگر همه پیام‌ها در یک صف باشند و یک کمپین میلیونی راه بیفتد، OTP ورود کاربر دقیقه‌ها معطل می‌ماند. جداسازی صف و اولویت، همان چیز است که در سیستم واقعی «احساس سرعت» می‌دهد.

**مفهوم نرم‌افزاری:**  
- Competing Consumers  
- Fair Dispatch  
- Back-pressure  
- جداسازی دغدغه‌ها بین QoS صف و concurrency اپلیکیشن  

---

### ۸) رویدادهای یکپارچه‌سازی (Integration Events)

**چه کار کردیم؟**  
رویدادهای داخل دامنه را از قراردادهای بین سرویس‌ها جدا کردیم.  
چیزهایی که بیرون باید بشنود (مثلاً «ارسال شد») روی exchange جدا منتشر می‌شوند و می‌توانند Webhook را تغذیه کنند.

**چرا؟**  
اگر سیستم بعدی مستقیماً به مدل داخلی تو وابسته شود، دیگر نمی‌توانی مدل را عوض کنی. قرارداد بیرونی باید پایدار و آگاهانه باشد.

**مفهوم نرم‌افزاری:**  
- Domain Event در برابر Integration Event  
- Anti-corruption در مرز سرویس  
- Event-driven integration

---

### ۹) امنیت به‌صورت مرحله‌ای (نه شعار)

**چه کار کردیم؟**  
سخت‌سازی تدریجی:

- احراز هویت با API Key و نقش‌ها  
- محدودیت نرخ (Rate limit)  
- CORS آگاهانه  
- هدرهای امنیتی  
- داشبورد Hangfire پشت کلید و محدودیت  
- جلوگیری از webhook به آدرس‌های ناامن داخلی  
- بررسی آسیب‌پذیری بسته‌های NuGet در CI  

**چرا؟**  
یک API اعلان‌رسانی اگر باز باشد، تبدیل می‌شود به رله اسپم. امنیت اینجا «ویژگی لوکس» نیست؛ بخشی از محصول است.

**مفهوم نرم‌افزاری:**  
- Defense in depth  
- Least privilege  
- Secure by default در تنظیمات Production  

---

### ۱۰) مشاهده‌پذیری (Observability)

**چه کار کردیم؟**  

- لاگ ساخت‌یافته با Serilog  
- Health check برای Postgres / Redis / RabbitMQ  
- آمادگی برای OpenTelemetry و Jaeger  
- ترکیب سرویس‌ها با .NET Aspire در محیط توسعه  

**چرا؟**  
بدون لاگ و متریک، وقتی پیام نمی‌رسد فقط می‌گویی «کار نمی‌کند». با observability می‌فهمی کدام مرحله شکست: قبول درخواست، outbox، صف، یا provider.

**مفهوم نرم‌افزاری:**  
- Three pillars: logs, metrics, traces  
- Health vs Ready  
- Composition در dev با Aspire (نه قاطی کردن orchestration کسب‌وکار با infra)

---

### ۱۱) تزریق وابستگی تمیز با Scrutor

**چه کار کردیم؟**  
به‌جای صدها خط `AddScoped` دستی، ثبت سرویس‌ها با قرارداد و نام‌گذاری یکدست (convention) و Scrutor انجام شد؛ موارد خاص (دکوراتور، چند پیاده‌سازی پلاگین) صریح ماندند.

**چرا؟**  
ثبت دستی در پروژه‌های بزرگ هم خطا می‌زاید هم merge conflict. Convention یعنی کمتر کد تکراری، بدون از دست دادن کنترل روی موارد حساس.

**مفهوم نرم‌افزاری:**  
- Convention over configuration  
- Composition Root تمیز  

---

### ۱۲) کارایی زمان اجرا (بدون قمار روی AOT)

**چه کار کردیم؟**  

- ReadyToRun برای کاهش cold-start  
- Dynamic PGO برای بهینه‌سازی مسیر داغ بعد از گرم شدن  
- Server GC + تنظیمات مدرن .NET 9 (مثل DATAS)  
- Native AOT را عمداً عقب انداختیم  

**چرا؟**  
این سیستم پلاگین، EF Core و Hangfire دارد؛ AOT الان بیشتر از سود، ریسک شکستن reflection می‌آورد. انتخاب مهندسی یعنی **بهترین تعادل**، نه پُرجذاب‌ترین گزینه در توییتر.

**مفهوم نرم‌افزاری:**  
- اندازه‌گیری قبل از بهینه‌سازی  
- Trade-off آگاهانه بین latency استارتاپ و سازگاری  

---

### ۱۳) پنل ادمین Next.js

**چه کار کردیم؟**  
یک کنسول وب در `apps/admin` که به API روی `localhost:5245` وصل می‌شود و سناریوهای واقعی را دستی می‌توان زد: ارسال، قالب، کمپین، workflow، رضایت، وب‌هوک، …

**چرا؟**  
Swagger برای توسعه‌دهنده خوب است؛ برای دیدن «کاربر ادمین چطور با سیستم حرف می‌زند» یک UI ساده خیلی گویاتر است.

**مفهوم نرم‌افزاری:**  
- جدا بودن Client از API  
- قرارداد OpenAPI به‌عنوان منبع حقیقت بین بک‌اند و فرانت  

---

## چه مفاهیمی را «به‌نحو احسن» پیاده کرده‌ایم؟

اگر بخواهیم روی دیوار بنویسیم:

| مفهوم | پیاده‌سازی در پروژه |
|--------|---------------------|
| **Microkernel / Plugin** | هسته ثابت + Plugins/* |
| **DDD (غنی)** | Aggregate، قانون در دامنه، نه فقط DTO |
| **Clean / Layered Architecture** | Domain → Application → Infrastructure → Host |
| **CQRS + MediatR** | Command/Query و Handler |
| **Result Pattern** | شکست کسب‌وکار بدون سوءاستفاده از Exception |
| **Transactional Outbox** | یک تراکنش برای state + پیام |
| **Inbox / Idempotency** | پردازش تکراری امن |
| **Message reliability** | Hangfire + reconciliation |
| **Queue design** | channel queues، critical path، DLQ، retry |
| **Integration Events** | قرارداد بیرونی جدا از دامنه |
| **Security hardening** | API key، rate limit، CORS، audit وابستگی‌ها |
| **Observability** | Serilog، Health، OTEL-ready |
| **DI conventions** | Scrutor |
| **Performance pragmatism** | R2R + PGO؛ AOT آگاهانه نه |
| **ADR-driven decisions** | تصمیم‌ها در `docs/ADR-*.md` ثبت شده‌اند |

---

## چرا این‌همه ADR؟

هر تصمیم مهم در پوشه `docs/` با شماره ADR آمده است.  

ADR یعنی: **چرا این کار را کردیم، چه گزینه‌هایی بود، چه عاقبتی دارد.**  

شش ماه بعد، خودت هم فراموش می‌کنی «چرا Hangfire و نه فقط یک BackgroundService». ADR همان حافظه تیم است.

## مسیر ذهنی یک پیام (جمع‌بندی داستان)

```text
ادمین / سیستم شما
        │
        ▼
   API (Host)  ─── احراز هویت، اعتبارسنجی، Result
        │
        ▼
 Application (MediatR)  ─── سناریو
        │
        ▼
    Domain  ─── قانون کسب‌وکار
        │
        ▼
  DB + Outbox  ─── همان تراکنش
        │
        ▼
 Hangfire / Worker  ─── انتشار به RabbitMQ
        │
        ▼
 صف کانال / critical
        │
        ▼
    Plugin  ─── SendGrid / Twilio / …
        │
        ▼
  وضعیت + (اختیاری) Webhook / Integration Event
```

این مسیر ساده به نظر می‌رسد؛ ارزش مهندسی در **همین جزئیاتی است که جلوی گم‌شدن، تکراری‌شدن، گرسنگی OTP، و وابستگی به یک provider** را می‌گیرد.

## آنچه عمداً انجام ندادیم (و افتخار هم هست)

- تبدیل همه چیز به Microservices از روز اول  
- Native AOT قبل از آماده‌شدن مرز پلاگین‌ها  
- قاطی کردن Exception با خطاهای عادی کسب‌وکار  
- یک صف واحد برای همه ترافیک  
- امنیت «بعداً درستش می‌کنیم»  

مهندسی خوب گاهی یعنی **نه گفتن** به پیچیدگی زودرس.

## برای مخاطب غیرتکنیکال

اگر فقط این را به یاد بسپاری کافی است:

> NotificationHub یک **مرکز پست هوشمند** برای پیام‌های محصول توست:  
> نامه را می‌گیری، مهر می‌زنی، در کیسه درست می‌گذاری، اگر پستچی نبود دوباره تلاش می‌کنی، و همیشه می‌دانی نامه کجاست —  
> بدون اینکه برای هر نوع نامه یک اداره جدا بسازی.
